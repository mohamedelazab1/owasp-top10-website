OWASP-A05:2021

Security Misconfiguration

Security misconfiguration is the most commonly seen issue, found in 90%+ of tested applications. It includes unpatched software, default credentials, exposed admin panels, verbose error messages, and insecure cloud storage.

Difficulty: Easy
Cloud Defaults Hardening

Real-World Incidents

Capital One Breach (2019) — 100M Records

A former AWS employee exploited a Server-Side Request Forgery vulnerability (A10 in our list — covered later) made possible by a misconfigured Web Application Firewall. The firewall had overly permissive IAM roles that allowed the attacker to query the EC2 metadata service and obtain temporary AWS credentials. Those credentials granted access to 100 million customer records including 140,000 Social Security numbers and 80,000 bank account numbers.

Capital One paid $190 million in settlements. The same misconfiguration pattern has been found in countless other companies with S3 buckets and similar setups.

Other Notable Incidents

  • Misconfigured S3 Buckets (2017-2020) — A huge wave of breaches: Accenture (137 GB), Verizon (6M customers), Booz Allen Hamilton (28,000 SSHs), Time Warner Cable (4M subscribers), and millions of others. The cause was almost always S3 buckets set to "Public" with a few clicks.
  • CloudPets (2017) — Smart toys leaked 2.2M voice recordings of children and families via an exposed MongoDB instance with no password.
  • Elasticsearch exposures — A Shodan study found over 4,000 Elasticsearch databases exposed without authentication, holding 1.1B+ records.
  • Default credentials (Honda, Nissan, etc.) — In 2022, researcher Sam Curry chained a few misconfigurations to remoted unlock and start Honda and Nissan cars from anywhere.
  • Microsoft Exchange ProxyLogon (2021) — Hafnium and 30+ APT groups exploited a misconfiguration in default Exchange deployments to install webshells on hundreds of thousands of orgs.

How It Works — The Misconfiguration Zoo

1. Cloud Storage Set to "Public"

The single most damaging misconfiguration. An S3 bucket, Azure Blob, or Google Cloud Storage bucket set to public exposes every file inside to the internet.

2. Default Credentials

Jenkins admin/admin, Tomcat manager/manager, Grafana admin/admin, MySQL root/no password, MongoDB no auth. Default creds are well-known and constantly scanned for.

3. Verbose Error Messages & Stack Traces

A production stack trace reveals file paths, framework versions, database types, and internal IP addresses — gold for an attacker planning the next step.

4. Directory Listing Enabled

The web server happily shows a file listing of /uploads/ or /backup/. Users browse the source code, backups, and config files.

5. Unpatched Software

The latest version of WordPress, Spring, Apache, or whatever's running has a public CVE. You never patched.

6. Outdated TLS / Weak Ciphers

SSLv3, TLS 1.0/1.1, RC4, 3DES, MD5-signed certificates — all still commonly found.

7. Unnecessary Features Enabled

Sample apps, debug consoles (e.g., /console on Rails in production), administrative interfaces left on, test endpoints.

Vulnerable Code & Config Examples

Example 1: Public S3 Bucket (Terraform)

Terraform (HCL)Vulnerable
resource "aws_s3_bucket" "customer_data" {
    bucket = "myapp-customer-data"
}

resource "aws_s3_bucket_acl" "customer_data" {
    bucket = aws_s3_bucket.customer_data.id
    acl    = "public-read"   // ❌ public-read = world-readable
}

# Even with a private bucket, a public bucket policy can expose it.
# The S3 console will then show a yellow "Public" badge.

Example 2: Spring Boot Actuator in Production

application.propertiesVulnerable
# ❌ Exposing all actuator endpoints to the world
management.endpoints.web.exposure.include=*
management.endpoint.health.show-details=always

# Attacker visits /actuator/env → sees ALL environment variables
# /actuator/heapdump → downloads the entire JVM heap (may include secrets)
# /actuator/threaddump → reveals internal class names, stack info

Example 3: Verbose Django Errors in Production

Django settingsVulnerable
# ❌ DEBUG = True in production
DEBUG = True

# Result: a 500 error page shows the full Python stack trace,
# local variables, Django version, database engine, secret_key,
# and clickable links to specific lines in your source code.
# This is the famous "yellow Django page of death."

Example 4: Default MongoDB No Authentication

MongoDB ConfigVulnerable
# /etc/mongod.conf
# ❌ No authentication enabled
security:
  authorization: disabled
bindIp: 0.0.0.0   # ❌ bound to all interfaces, not just localhost

# Result: anyone who can reach the port gets full DB access.
# MongoDB was the poster child for this in 2017 when ransomware
# gangs (e.g., "MongoDB Apocalypse") wiped 28,000 exposed servers.

Example 5: Apache Directory Listing

Apache httpd.confVulnerable
<Directory /var/www/uploads>
    Options Indexes FollowSymLinks   # ❌ Indexes enables directory listing
    AllowOverride None
    Require all granted
</Directory>

# Result: /uploads/ shows a list of every uploaded file.
# If /backups/ is also configured this way, full database dumps leak.

Attack Walkthrough — Finding Public S3 Buckets

1
Pick a target

Identify a company or project you're researching. Note its main domain and known asset domains.

2
Enumerate bucket names

Common patterns: {company}-backup, {company}-uploads, {company}-dev, {company}-data. Tools: S3Scanner, bucket-stream.

3
Test for public access

Try: aws s3 ls s3://target-bucket --no-sign-request or just curl https://target-bucket.s3.amazonaws.com/ in a browser. If a listing comes back, it's public.

4
Recursively download

aws s3 sync s3://target-bucket ./loot --no-sign-request — and the contents are now on your disk.

5
Report responsibly

Follow the company's security.txt / responsible disclosure process. Big bounties (often $5,000–$25,000) for public S3 buckets containing sensitive data.

Secure Configuration

1. Cloud Storage Defaults

Terraform (HCL)Secure
resource "aws_s3_bucket" "customer_data" {
    bucket = "myapp-customer-data"
}

# Block all public access at the account level
resource "aws_s3_bucket_public_access_block" "customer_data" {
    bucket = aws_s3_bucket.customer_data.id
    block_public_acls       = true
    block_public_policy     = true
    ignore_public_acls      = true
    restrict_public_buckets = true
}

# Use short-lived signed URLs for user uploads/downloads
resource "aws_s3_bucket_acl" "customer_data" {
    bucket = aws_s3_bucket.customer_data.id
    acl    = "private"
}

2. Production Hardening

Django settingsSecure
DEBUG = False
ALLOWED_HOSTS = ['app.example.com']

# Use Sentry, Rollbar, or your own logger to get stack traces internally
LOGGING = {
    'version': 1,
    'handlers': {'sentry': {'class': 'sentry_sdk.integrations.logging.EventHandler'}},
    'loggers': {'': {'handlers': ['sentry'], 'level': 'ERROR'}},
}

# Generic 500 page for users
handler500 = 'myapp.views.custom_500'

3. Hardened HTTP Headers

nginxSecure
server {
    listen 443 ssl http2;
    server_name app.example.com;

    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'nonce-...'" always;
    add_header Permissions-Policy "geolocation=(), microphone=()" always;

    # Disable detailed server tokens
    server_tokens off;
    more_clear_headers Server;
}

4. Disable Unnecessary Endpoints

For Spring Boot, lock down actuators:

application.propertiesSecure
# Only expose /health to anonymous users
management.endpoints.web.exposure.include=health
management.endpoint.health.show-details=never

# For internal actuator endpoints, require authentication
spring.security.user.name=${ACTUATOR_USER}
spring.security.user.password=${ACTUATOR_PASSWORD}

How to Test for It

  1. Run a vulnerability scanner — Nessus, Qualys, or OpenVAS will find unpatched software and default creds.
  2. Shodan / Censys — search for your own IPs and domains to see what's exposed.
  3. Check the dev tools — is DEBUG on? Is the source map exposed? Are there .git folders?
  4. Look for .env, .git, composer.json, package.json in production paths.
  5. Run an SSL Labs scan — grade your TLS config.
  6. Test every known default credential on every interface.
  7. Audit cloud storage permissions with tools like ScoutSuite or Prowler.

Tools

ScoutSuite / Prowler

Multi-cloud security auditing. Find public S3 buckets, IAM issues, etc.

Shodan

Search engine for internet-connected devices. Find your own exposed stuff.

Prevention Checklist

✅ Hardening Routine
  • Repeatable, automated hardening process. Bake it into your Terraform / CloudFormation / Ansible.
  • Disable any features you don't use (sample apps, debug consoles, default endpoints).
  • Change all default credentials. Use a password manager to track them.
  • Patch on a schedule — and patch critical CVEs within days, not months.
  • Disable directory listings everywhere.
  • Set custom error pages — never show stack traces in production.
  • Block public access to all cloud storage by default; only enable it with intent.
  • Set strict, security-focused HTTP response headers.
  • Run a quarterly configuration audit using an automated scanner.
