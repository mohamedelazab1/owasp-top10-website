Server-Side Request Forgery (SSRF)

SSRF flaws occur whenever a web application is fetching a remote resource without validating the user-supplied URL. The attacker can coerce the server to send a request to an unexpected destination — often inside the internal network or cloud metadata service.

Difficulty: Expert
SSRF Cloud Metadata Internal Pivot

Real-World Incidents

Capital One Breach (2019) — 100M Records via AWS Metadata

A former AWS employee exploited a Server-Side Request Forgery in Capital One's web application firewall. By sending http://169.254.169.254/latest/meta-data/iam/security-credentials/role-name as a URL to the vulnerable endpoint, the application made a request to the AWS Instance Metadata Service from the EC2 instance. The instance's IAM role had overly broad permissions — granting access to 100 million S3 objects containing customer data.

The breach cost Capital One $190 million in settlements. The same SSRF pattern has been found in dozens of other AWS-hosted applications.

Other Notable Incidents

  • Uber Breach (2016) — SSRF in a marketing site hit http://169.254.169.254/... on the company's cloud instance, dumping credentials. 57 million driver records stolen.
  • GitHub Enterprise (2017) — Internal server-side request forgery could read internal files and services. Patched within hours of disclosure.
  • Microsoft Power Apps (2021) — The OData API allowed anonymous users to query internal data sources (see A01). Some endpoints were reachable via SSRF.
  • Shopify Bug Bounty (multiple) — Researchers consistently find SSRF in Shopify's product image proxy. Several paid $10k-$25k bounties.
  • CloudBleed-related — Some CloudFlare features that fetched user-supplied URLs were vulnerable to internal SSRF.
  • Yahoo (2014) — Image processing servers had SSRF; the attacker could access internal admin panels.

How It Works

The Basic Pattern

Anywhere an application fetches a remote resource based on user input, you have an SSRF candidate:

  • Image / avatar / favicon proxy: https://app.com/proxy?url={user-url}
  • PDF generation from URL: https://app.com/render?url={page}
  • Webhook testing: https://app.com/check?url={webhook}
  • Import from URL: https://app.com/import?url={feed}
  • OAuth / OIDC callbacks (less common but devastating)

The Three Targets of an SSRF

  1. The server itself — bypass authentication, hit http://localhost/admin, retrieve cloud metadata.
  2. Other internal services — Redis, Elasticsearch, internal admin panels, Kubernetes API server, internal Prometheus, etc.
  3. External services — abuse as an open proxy, scan ports on third parties, attack internal services of a partner network.

The Cloud Metadata Service — The Juicy Target

Every cloud provider has a special internal IP that returns instance information:

  • AWS / EC2: 169.254.169.254 and (newer) 169.254.170.2 for ECS
  • GCP: metadata.google.internal (also 169.254.169.254)
  • Azure: 169.254.169.254 (with header requirement)
  • DigitalOcean: 169.254.169.254
  • OpenStack: usually 169.254.169.254

On AWS, hitting 169.254.169.254/latest/meta-data/iam/security-credentials/ returns the name of the IAM role attached to the instance. Then hitting .../security-credentials/<role-name> returns temporary AWS keys. With those keys, the attacker can assume the role and access whatever S3 buckets, databases, or services it has access to.

Vulnerable Code Examples

Example 1: Classic Image Proxy (Node.js)

Node.js (Express)Vulnerable
// ❌ Fetching a user-supplied URL with no validation
app.get('/proxy', async (req, res) => {
    const url = req.query.url;
    const response = await fetch(url);
    const buffer = await response.arrayBuffer();
    res.contentType(response.headers.get('content-type'));
    res.send(Buffer.from(buffer));
});

// Attacker calls: /proxy?url=http://169.254.169.254/latest/meta-data/
// The application makes the request FROM the EC2 instance
// and returns the metadata response to the attacker.

Example 2: PDF Generation (Python)

Python (wkhtmltopdf)Vulnerable
import subprocess

@app.route('/pdf')
def generate_pdf():
    url = request.args.get('url')
    # ❌ wkhtmltopdf fetches the URL — but also local file:// URLs!
    # Some versions also support JavaScript, opening XSS in the server
    result = subprocess.run(
        ['wkhtmltopdf', url, '/tmp/out.pdf'],
        capture_output=True, timeout=30
    )
    return send_file('/tmp/out.pdf')

# /pdf?url=file:///etc/passwd   → server returns the system file
# /pdf?url=http://localhost:6379/ → can probe internal services

Node.jsVulnerable
// ❌ A tool to test if your webhook works — fetches any URL
app.post('/test-webhook', async (req, res) => {
    const { url } = req.body;
    const result = await fetch(url, { method: 'POST', body: JSON.stringify(req.body) });

// Attacker can:

Attack Walkthrough — Capital One Style

1
Find an SSRF surface

The WAF or app has a feature that fetches user-supplied URLs. In Capital One's case, the WAF itself had the vulnerable endpoint.

2
Test the connection

Request http://169.254.169.254/. If the response is something other than a connection error, the application can reach the metadata service.

3
Enumerate the IAM role

Request http://169.254.169.254/latest/meta-data/iam/security-credentials/. Returns the name of the role attached to the instance (e.g., web-server-role).

4
Get the temporary keys

Request http://169.254.169.254/latest/meta-data/iam/security-credentials/web-server-role. Returns an AccessKeyId, SecretAccessKey, and Token valid for ~6 hours.

5
Configure the AWS CLI with the keys and pivot

aws configure with the stolen credentials, then aws s3 ls — see all the buckets. aws s3 sync s3://customer-data ./loot — exfiltrate the data.

Secure Approach

1. Network Egress Restrictions

The single most effective mitigation. By default, your application servers should not be able to reach arbitrary IPs.

  • AWS: use a Network Firewall, VPC security groups, or NAT gateway that only allows outbound traffic to a known allowlist of external services.
  • Block IMDSv1 and require IMDSv2 (which uses a token in a header, making it harder to exploit via SSRF).
AWS CLIRequire IMDSv2
# Disable IMDSv1 on the EC2 instance
aws ec2 modify-instance-metadata-options \
    --instance-id i-1234567890abcdef0 \
    --http-tokens required \
    --http-put-response-hop-limit 1

2. Validate the URL — DNS, scheme, and resolution

If you must allow users to supply URLs, validate them strictly. The validation should resolve the hostname and check the resulting IP against an allowlist (and block list for private ranges).

Node.js (using ssrf-req-filter)Secure
const ssrfFilter = require('ssrf-req-filter');

app.get('/proxy', async (req, res) => {
    const url = req.query.url;
    try {
        // ✅ Resolves the host, checks the IP, blocks private ranges
        const safeUrl = await ssrfFilter(url);
        const response = await fetch(safeUrl);
        res.send(await response.text());
    } catch (err) {
        res.status(400).send('URL not allowed');
    }
});

3. Use a Built-in Safe HTTP Client

Don't roll your own validation. Use a well-tested library.

  • node: ssrf-req-filter
  • python: ssrf-protect, mitmproxy-based approaches, or httpx with custom transport
  • go: safeurl
  • java: Apache HttpClient with RoutePlanner that blocks private IPs

4. Disable Unnecessary URL Schemes

Only allow http:// and https://. Block file://, gopher://, dict://, ftp://, ldap:// at the HTTP client or the URL parser.

5. Handle Redirects Safely

Even if you validate the initial URL, the server might respond with a 302 to http://169.254.169.254/. Always re-validate after redirects — or disable redirects.

Node.jsSecure
// ✅ Disable automatic redirects
const response = await fetch(url, { redirect: 'manual' });
if ([301, 302, 303, 307, 308].includes(response.status)) {
    // Re-validate the Location header before following
    const next = await ssrfFilter(response.headers.get('location'));
    return await fetch(next, { redirect: 'manual' });
}

Tools

Burp Collaborator

Out-of-band interaction server. Detects SSRF even when the response isn't returned.

Interactsh (open source)

Free alternative to Burp Collaborator. Probes DNS, HTTP, and SMTP for callbacks.

SSRFmap

Automated SSRF exploitation framework. Supports many bypasses and target services.

Gopherus

Generates gopher:// payloads to attack internal services (Redis, Memcached, etc.).

SwAG (SSRF on AWS Generator)

Generates payloads specifically for AWS SSRF scenarios.

Canarytokens

Quick & free DNS/HTTP tokens to detect when an SSRF is triggered.

Prevention Checklist

✅ Layered Defense
  • Apply network egress filtering: only allow outbound traffic to the specific external services you need.
  • Require IMDSv2 on AWS, equivalent on GCP / Azure.
  • Validate the URL: scheme allowlist, DNS resolution check, IP allowlist / blocklist (block all RFC 1918, link-local, loopback).
  • Disable HTTP redirects, or re-validate after every redirect.
  • Don't expose detailed error messages that reveal internal IPs or services.
  • Limit the IAM role of every instance to the bare minimum (least privilege).
  • For services that don't need to fetch URLs, don't add that capability. Avoid the feature creep.
