Cryptographic Failures

Previously known as "Sensitive Data Exposure," this category focuses on failures related to cryptography that lead to sensitive data exposure — weak algorithms, missing encryption, improper key management, or transmission of data in cleartext.

Difficulty: Easy
Back-end TLS/SSL Hashing Storage

Real-World Incident

Equifax Breach (2017) — 147 Million Records

The single biggest data breach in U.S. history at the time. Attackers exploited an Apache Struts vulnerability (CVE-2017-5638) to break into Equifax's dispute-resolution portal. They then moved laterally through the network, finding credentials and certificates stored in plaintext configuration files, allowing them to exfiltrate 147 million Americans' names, Social Security numbers, birth dates, addresses, and some driver's license numbers.

Cost to Equifax: $1.4 billion in total expenses, plus the resignation of the CEO, CIO, and CSO.

Other Notable Incidents

  • LinkedIn (2012) — 117 million passwords leaked because they were hashed with SHA-1 (no salt, single iteration). Cracked in days.
  • Yahoo (2013–2014) — 3 billion accounts compromised. The "encrypted" passwords used MD5 — broken in 2012.
  • Adobe (2013) — 153 million user records. Passwords encrypted with 3DES in ECB mode, which preserves patterns. Worse, the same 3DES key was used for every user.
  • CloudBleed (2017) — Cloudflare's edge servers leaked sensitive data in HTTP responses for months due to a buffer overflow in their HTML parser, including private keys, cookies, and HTTPS request bodies.
  • Adult Friend Finder (2016) — 412 million accounts. Passwords stored using a weak SHA-1 variant. 99% of passwords were cracked within weeks.

How It Works

Cryptographic failures happen in three broad ways:

1. Data in Transit Not Encrypted

The application uses HTTP instead of HTTPS, or uses HTTPS with weak ciphers. A network attacker (coffee shop Wi-Fi, hostile ISP) can read or modify all traffic.

2. Data at Rest Stored Insecurely

Sensitive data is stored in plaintext, with reversible "encryption" (Base64 is encoding, not encryption), or with weak algorithms like MD5, SHA-1, or DES.

3. Poor Password Hashing

Passwords are stored as plaintext, MD5/SHA-1 hashes (too fast — GPU can compute billions per second), or are hashed without a salt (enabling rainbow table attacks).

4. Improper Key Management

Encryption keys are hardcoded in source code, stored in the same database as the encrypted data, checked into Git, or never rotated.

5. Weak Random Number Generation

Session tokens, password reset links, and API keys generated with Math.random() or java.util.Random — both predictable. A Math.random() token can be brute-forced in minutes.

Vulnerable Code Examples

Example 1: Plaintext Password Storage (Node.js)

You'd be surprised how often this is still found.

JavaScript (Express)Vulnerable
// ❌ Storing the password as-is
app.post('/register', async (req, res) => {
    const user = {
        email: req.body.email,
        password: req.body.password  // plaintext in the database
    };
    await db.users.insert(user);
    res.send('Registered');
});

Example 2: MD5 Hashing (PHP)

MD5 is broken for password hashing. Modern GPUs compute ~50 billion MD5 hashes per second.

PHPVulnerable
// ❌ MD5 without a salt
$hash = md5($password);
// Database is breached → attacker recovers every password in hours
// Even with a salt, MD5 is far too fast for passwords

Real Attack Walkthrough — Cracking a Leaked MD5 Database

Imagine you have dumped a database with 1 million users, and the passwords are stored as md5(password) with no salt. Here's how an attacker would crack them.

1
Identify the hash type

Use hashid or hash-identifier to confirm the algorithm. The 32-character hex string is MD5.

2
Get a wordlist

Download rockyou.txt (14 million common passwords, ~133 MB). It comes from a real 2009 breach and is still devastatingly effective.

3
Run hashcat or John the Ripper

On a single modern GPU, hashcat tests 50+ billion MD5 hashes per second against a wordlist. Rockyou is exhausted in seconds.

4
Try rules and masks

Append common mutations: password1, Password!, p@ssw0rd. Cracks another 30% of accounts.

5
Credential stuffing

Try the recovered email/password pairs on Gmail, banking, and other services. Most users reuse passwords.

ShellCracking with hashcat
# Mode 0 = MD5, attack mode 0 = straight wordlist
hashcat -m 0 -a 0 hashes.txt rockyou.txt

# Output
# 5f4dcc3b5aa765d61d8327deb882cf99:password
# e10adc3949ba59abbe56e057f20f883e:123456
# 25d55ad283aa400af464c76d713c07ad:12345678
# 3,890,124 hashes recovered (out of 4,200,000) in 47 seconds

Secure Code — The Fix

1. Use bcrypt, scrypt, or Argon2 for passwords

These algorithms are intentionally slow, memory-hard, and automatically handle salting. They are the standard for password storage as of 2025.

Node.jsSecure
const bcrypt = require('bcrypt');

// Cost factor 12 = ~250ms on modern hardware — slow enough to be safe
const hash = await bcrypt.hash(password, 12);
await db.users.insert({ email, password: hash });

// Verify
const ok = await bcrypt.compare(password, user.password);

2. Force HTTPS everywhere

nginxSecure
server {
    listen 80;
    server_name app.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    ssl_protocols TLSv1.2 TLSv1.3;     # ✅ Modern TLS only
    ssl_ciphers HIGH:!aNULL:!MD5;     # ✅ Disable weak ciphers
    ssl_prefer_server_ciphers on;
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
}

3. Use a cryptographically secure RNG

JavaScriptSecure
// ✅ Browser
const token = crypto.getRandomValues(new Uint8Array(32));
const hex = Array.from(token, b => b.toString(16).padStart(2, '0')).join('');

// ✅ Node.js
const token = require('crypto').randomBytes(32).toString('hex');

4. Use a Key Management System (KMS)

Never hardcode keys. Use a KMS like AWS KMS, GCP Cloud KMS, Azure Key Vault, or HashiCorp Vault.

Python (with AWS KMS)Secure
import boto3
kms = boto3.client('kms')

def encrypt_data(plaintext):
    response = kms.encrypt(
        KeyId='alias/my-app-key',
        Plaintext=plaintext
    )
    return response['CiphertextBlob']

# The actual encryption key never leaves the KMS service

5. Use modern authenticated encryption

Node.jsSecure
// ✅ AES-256-GCM provides both confidentiality and integrity
const crypto = require('crypto');

function encrypt(plaintext, key) {
    const iv = crypto.randomBytes(12);
    const cipher = crypto.createCipheriv('aes-256-gcm', key, iv);
    const enc = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
    const tag = cipher.getAuthTag();
    return Buffer.concat([iv, tag, enc]);
}

How to Test for It

  1. Inspect every endpoint over HTTP and HTTPS — is the login form on HTTP? Is the API available on port 80?
  2. Test the TLS configuration — use SSL Labs for a free, thorough scan. Look for old protocol versions, weak ciphers, and missing HSTS.
  3. Check for sensitive data in cookies and storage — open DevTools, look for tokens, passwords, or PII in cookies or localStorage.
  4. Test the password reset flow — is the reset token predictable? Can you use a token from one account to reset another?
  5. Look for hardcoded secrets — grep the public source code, JS bundles, mobile app APKs, and Git history for keys and tokens.
  6. Inspect the database schema — if you can, look at the type/length of password columns. MD5 is 32 hex chars; bcrypt is 60 chars starting with $2.

Prevention Checklist

✅ Modern Crypto Hygiene
  • Classify data and apply controls based on sensitivity (PII, payment, health, etc.).
  • Encrypt all data in transit with TLS 1.2+ (preferably 1.3). Redirect HTTP → HTTPS.
  • Encrypt sensitive data at rest using authenticated encryption (AES-GCM, ChaCha20-Poly1305).
  • Use bcrypt, scrypt, or Argon2 for password hashing. Never roll your own.
  • Generate keys with a CSPRNG and store them in a KMS or HSM. Rotate regularly.
  • Disable weak ciphers, MD5, SHA-1, DES, 3DES, RC4 in your stack.
  • Set strong HTTP headers: HSTS, Secure/HttpOnly/SameSite cookies, Content-Security-Policy.
