OWASP-A09:2021

Security Logging & Monitoring Failures

Without logging and monitoring, breaches cannot be detected. Insufficient logging, missing alerts, and the inability to investigate and respond to incidents in time allow attackers to persist in compromised systems for months.

Difficulty: Hard
SIEM IR Detection

Real-World Incidents

Target Breach (2013) — 110M Cards

Target's point-of-sale systems were infected with malware (BlackPOS / Kaptoxa) that scraped 40 million payment cards over 19 days. Target's security tools actually generated alerts — FireEye's intrusion detection flagged the malware on November 30, 2013. The SOC team in Bangalore received the alert, escalated it to headquarters, but no one acted on it. The attackers persisted for two more weeks, exfiltrating 11GB of card data. Target paid $292 million in settlements, and the CISO resigned.

Other Notable Incidents

  • Equifax (2017) — Attackers were inside Equifax's network for 76 days before being detected. The expired SSL certificate on the monitoring system meant alerts were never sent.
  • Capital One (2019) — The attacker, a former AWS employee, was inside the network for 4 months before a tipster email alerted the company. By then, 100M records had been exfiltrated.
  • SolarWinds (2020) — The malicious code was in SolarWinds' builds for over a year before FireEye discovered it while investigating their own breach.
  • Maersk / NotPetya (2017) — The destructive malware spread across Maersk's global network in 7 minutes, encrypting 49,000 devices. The single domain controller in their DHCP range was unpatched. Maersk reported $300M in damages.
  • Yahoo (2013-2014) — The breach was only disclosed in 2016, two years after discovery, which itself was three years after the breach.
  • Marriott (2018) — Attackers inside Marriott systems for 4 years (since 2014, when Starwood was compromised). 339 million guest records exposed.

How It Works — The Detection & Response Gap

Most breaches follow a similar pattern. Mandiant's M-Trends report says the global median dwell time (time between intrusion and detection) is around 10 days, but in some industries it's still measured in months.

1. The Attacker's Typical Kill Chain

  1. Initial access (phishing, exposed RDP, vulnerable web app)
  2. Establish persistence (web shell, scheduled task, startup item)
  3. Privilege escalation (mimikatz, token impersonation)
  4. Credential dumping and lateral movement
  5. Data discovery and staging
  6. Exfiltration (over days or weeks)

Every step is detectable — but only if you're logging, correlating, and alerting on the right signals.

2. Common Detection Failures

  • Authentication events (success AND failure) aren't logged, or aren't retained.
  • Logs are stored on the same host as the application (deleted in the breach).
  • No central SIEM, no correlation rules, no automated alerting.
  • Alerts go to a distribution list with no on-call rotation.
  • No incident response plan. No runbooks. No practice drills.
  • No metrics — the team doesn't know their MTTD (mean time to detect) or MTTR (mean time to respond).

Vulnerable Code Examples — What NOT to Log

Example 1: Logging Passwords & Sensitive Data

Node.js❌ Multiple Problems
// ❌ Logging the full request body including the password
app.post('/login', (req, res) => {
    console.log('Login attempt:', req.body);
    // Now the password is in plain text in /var/log/app.log
    // and shipped to your log aggregator (Datadog, Splunk, etc.)
    // If ANY of those are breached, you have a credentials dump.
});

Example 2: No Logging at All on Auth Events

Python (Flask)Vulnerable
@app.route('/login', methods=['POST'])
def login():
    user = db.users.find_one({'email': request.json['email']})
    if user and bcrypt.checkpw(request.json['password'], user['password']):
        session['user_id'] = user['_id']
        return {'status': 'ok'}
    return {'status': 'fail'}, 401

# ❌ No logging of:
#   - failed login attempts
#   - successful logins (with timestamp, IP, user agent)
#   - subsequent privileged actions
# An attacker brute-forcing 10k passwords leaves no trace.

Example 3: Catch-All Exception Handler that Swallows

Node.jsVulnerable
// ❌ Catch errors and just return 500
app.use((err, req, res, next) => {
    res.status(500).send('Something went wrong');
});
// The error is gone. No record of:
#   - the SQLi attempt that caused it
#   - the request that triggered it
#   - the user that tried it
# Perfect for an attacker — silent probing is invisible.

Attack Walkthrough — Staying Hidden in Plain Sight

This is what a sophisticated attacker does once inside, knowing that lack of logging is often the biggest weakness.

1
Use legitimate credentials

Don't create new accounts. Use stolen, valid credentials for the application's own users (perhaps purchased from a credential dump). The application sees a "valid" login.

2
Slow down exfiltration

Don't dump the entire DB in one query. Take 50 records per hour over 6 months. Avoids any "large export" alerts.

3
Blend with normal traffic

Use the same endpoints real users use. Don't probe hidden admin paths (which would log 404s). Don't use a vulnerability scanner (which would log 1000s of 4xx responses).

4
Use application's own functionality

Use the export-to-CSV feature to download data. Use the bulk email feature to send phishing. Use the file upload to plant a webshell that looks like a user's image.

5
Disable or tamper with logs

If the attacker gets RCE on a server, the first thing they do is rm -rf /var/log/* or modify the application to stop logging. A good detection program sends logs off-host in real time, so this is harder.

Secure Approach — A Modern Detection Stack

1. Structured Application Logging

Node.js (pino)Secure
const pino = require('pino');
const logger = pino();

app.post('/login', loginLimiter, async (req, res) => {
    const { email, password } = req.body;
    const user = await db.users.findOne({ email });

    // ✅ Always run bcrypt to prevent timing attacks
    const ok = user && await bcrypt.compare(password, user.password);

    if (!ok) {
        // ✅ Log failures with enough context to detect brute force
        logger.warn({
            event: 'auth.failure',
            email,
            ip: req.ip,
            userAgent: req.get('user-agent'),
            timestamp: new Date().toISOString(),
        }, 'Login failed');
        return res.status(401).send('Invalid');
    }

    // ✅ Log successful logins — used to detect impossible travel
    logger.info({
        event: 'auth.success',
        userId: user.id,
        ip: req.ip,
        userAgent: req.get('user-agent'),
    }, 'Login successful');
    res.send('ok');
});

2. Never Log Sensitive Data

Node.js (pino redaction)Secure
const logger = pino({
    redact: {
        paths: [
            'req.headers.cookie',
            'req.headers.authorization',
            'req.body.password',
            'req.body.token',
            'req.body.creditCard',
            '*.password',
            '*.secret',
            '*.apiKey',
        ],
        censor: '[REDACTED]',
    },
});

3. Detection Rules (Sigma format — vendor-neutral)

Sigma rule (YAML)Detection Engineering
title: Brute Force Login Attempts
status: stable
logsource:
    product: webserver
    category: application
detection:
    selection:
        event: 'auth.failure'
    timeframe: 5m
    condition: selection | count() > 20 by ip
    # 20+ failed logins from the same IP in 5 minutes → alert
fields:
    - email
    - userAgent
level: high
description: Detects credential brute-forcing attempts.

4. Centralized Logging with a SIEM

Send logs from all systems (apps, servers, cloud, network) to a SIEM like Splunk, Elastic, Sentinel, or Sumo Logic. Correlate across sources.

  • WAF logs + app logs — see the full request context for a blocked attack
  • Auth logs + VPN logs — detect a session token replayed from a new IP
  • DB logs + app logs — detect a query from a compromised user account that returns 100x normal data

5. Build an Incident Response Plan

  • Document roles (who's on call, who has authority to make decisions).
  • Build runbooks for common scenarios (data breach, ransomware, DDoS).
  • Run tabletop exercises quarterly.
  • Have a pre-drafted customer communication template.
  • Pre-stage tools: forensic image scripts, network captures, EDR queries.
  • Practice — most teams discover their IR plan is broken during their first real incident.

Tools

Splunk / Elastic / Sentinel

SIEM platforms. Centralize logs, search, and alert.

Sigma rules

Vendor-neutral detection rule format. Use the public Sigma repo for free, battle-tested rules.

OSQuery / Fleet

Endpoint telemetry as SQL queries. Great for hunting.

Falco / Tetragon

Runtime security for Kubernetes. Detects anomalous process and network behavior.

Sentry / Rollbar / Datadog

Application error monitoring. Sends alerts on unusual exception rates.

Velociraptor / GRR

Digital forensics / incident response tools for live systems.

Prevention Checklist

✅ A Defensible Detection Program
  • Log authentication events (success and failure), access control failures, and validation failures — with sufficient context (user, IP, UA, timestamp).
  • Generate logs in a format your SIEM can ingest (JSON over syslog, or via Filebeat/Vector).
  • Redact sensitive data before logging. Test for it in CI.
  • Set up detection rules for brute force, impossible travel, mass data access, and other common patterns.
  • Establish or subscribe to a threat intel feed — know which CVEs and TTPs matter to your stack.
  • Send logs off-host in real time. Store immutable backups (e.g., write-only S3 buckets with object lock).
  • Build and practice an incident response plan. Test it with a tabletop exercise quarterly.
  • Track MTTD and MTTR. Set a goal. Improve it.
