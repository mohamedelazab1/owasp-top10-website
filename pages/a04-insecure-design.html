Insecure Design

Insecure design is a broad category representing different weaknesses, expressed as "missing or ineffective control design." It differs from insecure implementation: even perfect code cannot fix an insecure design.

Difficulty: Medium
Design Business Logic Architecture

Real-World Incidents

Parler Data Scraping (2021) — 70M Posts

The "free speech" social network Parler infamously had 70 million posts scraped — including deleted ones, with location metadata — because the API was designed without rate limiting, and used sequential integer IDs. A researcher simply enumerated IDs 1 to 99,999,999 and pulled every post. The platform was offline shortly after. This is a textbook insecure design: no abuse-prevention controls were built into the architecture.

Other Notable Incidents

  • Robinhood (2020) — A 17-year-old social-engineered a customer support rep and got control of a high-net-worth account. The design assumed voice-based verification was safe — no defense in depth.
  • Strava Heatmap (2018) — The fitness app published a global heatmap that inadvertently revealed the locations of secret military bases. The design didn't consider sensitive infrastructure.
  • Twitter 'fleets' bug (2021) — A logic flaw in the design of Twitter's disappearing "fleets" feature on Android let attackers view fleets from any account, including protected ones, by simply changing the URL.
  • Verkada Cameras (2021) — Researchers found 150,000 security cameras (in hospitals, prisons, Tesla factory) accessible because the design used a "super admin" account whose credentials had been left in a publicly accessible internal app.
  • Snapchat Snappening (2014) — Third-party app design weakness allowed mass collection of "deleted" Snaps. The platform's API was designed to trust any client.

How It Works — Design Flaw Categories

1. Missing Rate Limiting

Endpoints that should be slow (login, password reset, account lookup) accept unlimited requests, enabling brute force, scraping, and account enumeration.

2. Trusting the Wrong Client

API returns sensitive data and trusts the client to filter it. Or assumes a "premium" tier check is sufficient when a user can change a role cookie.

3. Workflow Bypass

A multi-step process (signup → email verify → phone verify → payment) lets attackers skip steps and submit the final state directly.

4. Race Conditions in Business Logic

Two simultaneous withdrawals, two coupon redemptions, two votes. The design doesn't lock the resource, so both succeed.

5. Insecure Defaults

New features ship with "convenience" defaults like open sign-up, public profiles, or bypassed review.

Vulnerable Design — Real Code Patterns

Example 1: Coupon Race Condition

Python (Flask)Vulnerable Design
@app.route('/redeem', methods=['POST'])
def redeem_coupon():
    code = request.json['code']
    coupon = db.coupons.find_one({'code': code})
    if not coupon['used']:
        db.coupons.update_one({'_id': coupon['_id']}, {'$set': {'used': True}})
        user.balance += coupon['value']
        return {'ok': True}
    return {'error': 'already used'}

# ❌ TOCTOU (Time-of-check to time-of-use) bug
# Attacker sends 50 simultaneous requests → all see used=False → all get credit
# Fix: use an atomic update with a precondition
# db.coupons.update_one({'_id': id, 'used': False}, {'$set': {'used': True}})

Attack Walkthrough — Coupon Race Condition

1
Discover the endpoint

Sign up, find the "redeem coupon" feature, and capture the exact request in Burp.

2
Send it in parallel

Right-click the request in Burp → "Send to Intruder" → set null payload positions → set threads to 50 → start the attack.

3
Check the response

All 50 requests return 200 OK and your balance increased 50x. The coupon was redeemed 50 times.

4
Repeat with $1M of free credit

Hit a real e-commerce site in 2020 that shipped this exact bug — researchers redeemed the same $100 coupon hundreds of times before someone noticed.

Secure Design

1. Build threat models before writing code

For every feature, ask: who can call this? What's the abuse case? What if they call it 1,000 times per second? Use OWASP's Threat Dragon or Microsoft's STRIDE.

2. Use established patterns

For workflows, use a state machine. For sensitive operations, use an idempotency key. For pagination, use opaque cursors, not offset=12345.

3. Rate limit at multiple layers

Limit per-IP, per-account, per-API-key, per-endpoint. Use Redis sliding windows. Apply stricter limits to unauthenticated endpoints.

Node.js (Express + express-rate-limit)Secure
const rateLimit = require('express-rate-limit');

const loginLimiter = rateLimit({
    windowMs: 15 * 60 * 1000,  // 15 minutes
    max: 10,                    // 10 attempts per window
    message: 'Too many login attempts, try again later',
    standardHeaders: true,
    legacyHeaders: false,
});

app.post('/login', loginLimiter, async (req, res) => { /* ... */ });

4. Atomic state transitions

# ✅ Atomic: only succeeds if 'used' is still False
result = db.coupons.update_one(
    {'_id': coupon_id, 'used': False},
    {'$set': {'used': True, 'used_by': user_id, 'used_at': datetime.utcnow()}}

if result.modified_count == 0:
    return {'error': 'already used'}
user.balance += coupon['value']
user.save()

Prevention Checklist

✅ Secure by Design
  • Establish a secure development lifecycle (SDL) with threat modeling at design time.
  • Use established libraries and design patterns — don't reinvent auth, payments, or workflows.
  • Write abuse cases alongside user stories. "What can a logged-in user do that they shouldn't?"
  • Segment tenants and apply resource quotas per tenant.
  • Make all sensitive operations idempotent.
  • Apply rate limiting and resource limits at the gateway, not just in the application.
  • Document assumptions and constraints — e.g., "we assume the user is human" → add a CAPTCHA for high-value flows.
